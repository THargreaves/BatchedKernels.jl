# M6: forced hybrid storage measurements

The hybrid path now supports fresh register matrix values, single/register transfers,
and mixed shared/register compute. Ordinary broadcast still uses the legacy planner.
This report records a throughput decision gate, not an automatic optimizer.

## Reproduce

Run from the repository root with Julia 1.12.6 and production
`debug_accessors=false` preferences:

```sh
OPENBLAS_NUM_THREADS=1 julia --project=. benchmarking/kalman/hybrid_m6.jl
```

`BK_M6_N` selects the batch size (default 8192), `BK_M6_DIMS` the comma-separated
Kalman dimensions (default `8,16,32`), and `BK_M6_PROBES=false` skips the narrow-RHS
probes. The default run compares seven assignments at 128 threads; selected
legacy/single/register alternatives at 64 and 256 threads; and extra 32/64-thread
candidates for dimension 32, where static shared memory limits feasibility.

The unchanged kernel definitions in `../benchmarks/bench_kalman/ours_register.jl`
provide a handwritten prototype anchor at its original 256-thread geometry. Its
unrelated BenchmarkTools timing helper is not loaded. It must pass the same
correctness and zero-local-memory admission as every other candidate.

All covariance inputs are fixed during timing and checked afterwards. Each candidate
is compared over the entire batch with a CPU upper-triangle Cholesky reference.
Incorrect, spilling, or unlaunchable candidates are recorded but never timed.
Compilation and the exact timing path are warmed separately. Nine randomized rounds
measure batches of 20 kernel launches with CUDA events; the report uses medians and
quartiles. A separate wall-clock sample includes cached `fuse`, output allocation,
launch and synchronization. The prototype's corresponding sample allocates and
launches directly, since it has no `fuse` interface.

`compile_s` records uncached host compilation setup plus device compilation, excluding
input/output preparation and construction of the forced assignment. It is not total
process startup time. The forced path also incurs per-call assignment-key construction
and host output assembly. Kernel throughput and public call latency must be judged
separately. CPU activity elsewhere on this shared machine can affect wall-clock times.

Logical GB/s counts batched inputs and output once per launch. It is **not measured
DRAM traffic**: repeated launches reuse a warm working set that can fit in L2. Shared
inputs, shared-memory transfers and shuffle traffic are not counted in that number.
No clock settings were changed.

Nsight reproduction (warm caches retained):

```sh
ncu --profile-from-start off --cache-control none --metrics \
sm__warps_active.avg.pct_of_peak_sustained_active,dram__bytes.sum,dram__bytes.sum.per_second,l1tex__t_sectors_pipe_lsu_mem_local_op_ld.sum,l1tex__t_sectors_pipe_lsu_mem_local_op_st.sum \
julia --project=. benchmarking/kalman/hybrid_m6_profile.jl
```

## Assignment definitions

| Policy | Input placement | Compute results |
|---|---|---|
| legacy | Legacy dual | Legacy bodies and allocator |
| dual | Dual | Legacy bodies, conservative new allocator |
| single | Single | Row variants, single results |
| input_register | Register | Row variants, single results |
| register | Register | Row variants, register results |
| balanced_mul | Register | Matmul/add/sub registers; factorization/solves single |
| balanced_factor | Register | Factorization/solves registers; other results single |

All global I/O stages use single storage. All four common matrices stay in dedicated
shared input buffers. The narrow-RHS probes additionally compare column variants.

## Results (2026-09-08)

RTX 4090 (sm89, 24 GiB), NVIDIA driver 560.35.03; Julia 1.12.6, LLVM 18.1.7,
CUDA runtime/compiler 12.9, CUDACore 6.1.1, GPUCompiler 1.13.3.
Measurements use the M6 implementation accompanying this report, based on parent
commit `a0d0415`. [Raw timing rows](m6_results.csv) include resources and quartiles.
Local reproduction/admission logs are in the ignored research directory
`research/split_storage_plan/m6_validation/`.

Fastest admitted legacy and register-heavy configurations among the tested choices:

| D | Batch | Legacy threads | Register threads | Legacy kernel | Register kernel | Speedup |
|---|---:|---:|---:|---:|---:|---:|
| 8 | 8192 | 64 | 128 | 13.11 µs | 10.19 µs | 1.29× |
| 16 | 8192 | 128 | 128 | 70.66 µs | 51.15 µs | 1.38× |
| 32 | 8192 | 64 | 128 | 802.41 µs | 374.32 µs | 2.14× |
| 32 | 131072 | 64 | 128 | 12.41 ms | 5.85 ms | 2.12× |

The last row has 1 GiB of logical batch I/O, exceeding L2 capacity, and follows the
historical benchmark's approximately 1 GB working-set target. Reproduce it with
`OPENBLAS_NUM_THREADS=1 julia --project=. benchmarking/kalman/hybrid_m6_streaming.jl`.
It compares legacy, register-heavy, and the best smaller balanced-multiply geometry.
The balanced configuration takes 11.65 ms, close to legacy. All timed configurations
have zero compiled local-memory bytes and pass full-batch CPU comparisons.

At D=16/128 threads, register-heavy uses 168 registers and 12668 shared bytes versus
legacy's 96 registers and 30236 shared bytes. Balanced-multiply ties register-heavy's
51.15 µs while using 144 registers and 29564 shared bytes. At D=32/128 threads,
register-heavy reaches 255 registers but remains local-memory-free and uses 33788
shared bytes. Legacy at that geometry needs 67580 bytes, beyond the device's 49152
static per-block limit. Smaller legacy blocks remain feasible; the throughput table
compares against those, rather than treating a failed launch as a speedup.

Occupancy is not a sufficient ranking rule. At D=8/128, single-heavy is faster than
legacy despite lower theoretical occupancy (41.7% versus 50%). At D=16/128,
register-heavy and legacy both have 25% theoretical occupancy but differ by 1.38×.
The peak-register-element proxy also cannot distinguish the D=16 register-heavy and
balanced-multiply allocations: both report 64 elements but compile to 168 and 144
physical registers respectively.

Nsight Compute's separate warm-cache capture at D=16/batch 8192/128 threads measured
22.31%, 15.52% and 22.07% active-warp occupancy for legacy, single-heavy and
register-heavy. All three reported zero local load/store sectors. DRAM traffic was
0, 0 and 128 bytes respectively during these captures, confirming that this small
working set is cache-resident; those samples do not measure streaming bandwidth.
`--cache-control none` deliberately preserves the warmed cache state and does not
claim a reproducible cold-cache hardware-traffic measurement.

For `(32×32)*(32×2)`, the register row and column kernels take 65.73 and 19.87 µs,
using 128 and 56 registers. For the corresponding upper-triangular solve they take
48.54 and 30.15 µs, using 115 and 64 registers. Column placement lowers the live
matrix-element proxy from 96 to 36. Even the single-storage matmul improves from
74.79 to 25.74 µs when changing orientation, demonstrating that access pattern and
work distribution matter beyond occupancy. These are full transfer/compute/store
kernels, rather than the earlier isolated body microbenchmarks.

The unchanged handwritten prototype passes correctness but uses 160, 288 and 544
local bytes/thread at D=8,16,32. It is excluded from timing by the same admission
rule as other candidates. Local memory here is not proof of hardware register
exhaustion: its physical register counts are only 71, 87 and 69.

Public-call latency is a separate issue. At batch 8192, register-heavy is slower
than legacy at D=8 and D=16 in these wall-clock samples, despite better kernel times.
At D=32/batch 131072, it improves from 15.55 to 9.66 ms. Forced assignment-key
construction, allocation, output assembly, launch, synchronization and CPU scheduling
are included; this experiment does not isolate which host costs dominate. There is
no general end-to-end speedup claim for small batches.

## Decision and remaining scope

The storage backend passes the throughput/feasibility gate. Its role is to implement
optimized batched kernels and expose storage/variant choices. Candidate generation
may be heuristic; there is no claim of globally optimal storage selection. Validate
constraints, inspect actual compiled resources, measure promising candidates and cache
the selection. Keep forced assignments and the legacy default. CSP/DP can be added
later if useful for candidate generation; it is not required to establish the value
of the framework. The coarse policies tested here are examples, not a sufficient
universal optimizer.

The default first-call budget remains **one selected compilation and zero tuning
trials**; M6 introduces no hidden search. Uncached setup/device compilation reached
39 seconds for D=32 register-heavy on this machine, so multi-candidate search should
be explicit and budgeted before it is added. A prepared cached execution interface
is worth evaluating before claiming public latency improvements for small batches.

No new dimension or thread-count cap is introduced. Existing Float32 variant coverage,
shared-only forced mutation, shared input/vector residences, conservative fresh shared
outputs, and single global staging remain. Unsupported register-backed logical wrappers
are rejected on the host; existing legacy/shared wrapper support is preserved. The
255-register large kernel is a measured result for this toolchain, not a promise
that larger fusions will avoid local memory.


## Validation

Final production fuser/scheduler regression: **481/481 assertions**, including 24 new
selected CPU/GPU assertions. The 71 focused hybrid/register GPU assertions pass
production memcheck and racecheck, plus debug-mode synccheck, with zero errors or
race hazards. Public output inference checks pass. The small fused register solve
uses 40 registers, 720 shared bytes and zero local bytes in production. Diagnostics
add instrumentation and local memory; they are not used for resource admission or
timing.

Debug validation found that an input transfer had used the broadcast accessor with
lane-varying indices. It now uses ordinary indexed shared loads, which are the same
production loads; the uniformity diagnostics were preserved. Final production
regression and memcheck were rerun after this correction. Independent agent reviews
covered planner admission, generated participation, wrapper handling and benchmark
comparability.


## Focused five-slot follow-up (2026-09-14)

The current scheduler requires four legacy matrix slots when only P/H are batched,
and five when all five inputs are batched. The follow-up uses the verified five-slot
trace at D=32, batch 8193, and 32 threads for every candidate. All five inputs remain
batched in every candidate; shared residence does not change their batch semantics.
GPU/toolchain provenance is unchanged. Full-batch CPU comparisons and input-preservation
checks pass; every candidate has zero compiled local-memory bytes.

| Candidate | Registers/thread | Shared bytes/block | Kernel median |
|---|---:|---:|---:|
| Legacy | 167 | 21116 | 861.75 µs |
| Register-heavy | 255 | 4220 | 656.03 µs |
| Shared inputs, register results | 224 | 25340 | 1007.57 µs |

Register-heavy remains fastest in this selected case. The hybrid candidate reduces
register pressure but loses throughput; this does not establish that register-heavy
is always optimal whenever feasible. Register-heavy uses column storage for A/H and
the final two products to satisfy accessor contracts. The hybrid uses dual-access
shared inputs and row compute variants, so the comparison includes orientation and
staging costs. There is no exhaustive search or general heuristic claim.

Reproduce with `OPENBLAS_NUM_THREADS=1 julia --project=. benchmarking/kalman/hybrid_five_slots.jl`.
Detailed timings/resources are in [five_slots_results.csv](five_slots_results.csv).
No further optimizer study is required for the agreed framework positioning.


## Selective one/two-slot hybrid follow-up (2026-09-14)

This comparison keeps the five-input batched Kalman workload, D=32/batch 8193, seed
and compute variants fixed, and changes individual residences. Candidates share H,
predicted covariance, the Cholesky factor, or H plus predicted covariance. The planner
asserts **one or two single-access slots in total, including I/O staging, and zero
dual slots**. Intermediate-only placements can reuse the staging slot. All numerical
comparisons cover the full batch, and inputs remain unchanged after timing.

The first pass kept row output staging. All candidates remained at 255 registers,
with little throughput improvement. Inspection identified that the column register
result was being materialized into row staging via full-group broadcasts. Matching
column staging instead uses an owned-line copy, followed by the existing coalesced
global writer; the logical output layout is unchanged.

This ostensibly cheaper staging choice changes compiler resource allocation:
register-heavy uses 120 local bytes/thread; sharing only predicted covariance or the
factor uses 72. Sharing H, or H plus predicted covariance, eliminates that local
memory. These figures hold at both 32 and 128 threads. All candidates pass numerical
checks, but spilling candidates are excluded from timing. See
[selective_admission.csv](selective_admission.csv) for both staging passes.

The final comparison measures the spill-free register baseline (row staging) and the
best selective hybrid (column staging) together, with randomized order and the same
warm-up and nine-round timing policy as M6:

| Candidate | Threads | Single slots | Registers/thread | Shared bytes/block | Kernel median |
|---|---:|---:|---:|---:|---:|
| Register-heavy, row staging | 32 | 1 | 255 | 4220 | 657.45 µs |
| Shared H, column staging | 32 | 2 | 255 | 8444 | 506.77 µs |
| Register-heavy, row staging | 128 | 1 | 255 | 16880 | 666.37 µs |
| Shared H, column staging | 128 | 2 | 255 | 33776 | 490.34 µs |

The hybrid is **1.30×/1.36× faster at matched thread counts**, or **1.34× faster
comparing the best tested configurations**. All four are local-memory-free and have
16.67% theoretical occupancy. This is not an occupancy win: selective shared residence
enables a cheaper staging path without spills. The comparison includes this interaction
between storage and staging; it is not an isolated residence-only speedup. The live
matrix-element proxy falls from 192 to 160, while physical registers remain at 255.
Sharing H plus predicted covariance was slightly slower than sharing H alone.

This demonstrates a useful role for selective **single-access** shared storage in
this workload. It does not establish a universal policy or a performance benefit for
dual storage. No framework/codegen changes or new restrictions were needed.

Reproduce with `OPENBLAS_NUM_THREADS=1 julia --project=. benchmarking/kalman/hybrid_selective.jl`.
Set `BK_SELECTIVE_FINALISTS=true` for the four-row controlled comparison, whose data
is in [selective_results.csv](selective_results.csv). `BK_SELECTIVE_N` changes the batch
size and `BK_SELECTIVE_VALIDATE_ONLY=true` omits timing for sanitizer runs. Local raw
logs are in `research/split_storage_plan/m6_validation/selective*.log`.

The controlled finalists also pass CUDA memcheck at batch 5 (including a partial
128-thread block), with zero errors and unchanged inputs. Timing is disabled in
that sanitizer run.
